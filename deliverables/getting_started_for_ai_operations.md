# AI 운영 입문 가이드

이 문서는 AI CLI와 Workflow Engine을 처음 사용하는 사람이 Schema Workflow Operations Dashboard를 안전하게 시작하기 위한 안내서입니다.

## 1. 이 도구를 한 문장으로 이해하기

AI에게 맡긴 작업의 **요청, 실행 기록, 근거, 산출물과 사용자 확인 상태를 프로젝트별로 연결해 보는 로컬 대시보드**입니다.

AI를 더 똑똑하게 만드는 도구라기보다, AI 작업이 길어졌을 때 다음 내용을 놓치지 않게 돕습니다.

- 처음 요청한 목표
- 현재 진행 중인 작업
- 결과가 만들어진 위치
- 결과를 뒷받침하는 근거
- 자동 검증과 사용자 판단의 차이
- 다음에 이어서 해야 할 행동

## 2. 먼저 알아둘 세 가지

### 대시보드가 AI를 대신하지 않습니다

Codex, Claude Code와 Antigravity가 실제 분석과 파일 작업을 수행합니다. 대시보드는 실행을 준비하고 결과를 읽어 정리합니다.

### 통과가 최종 승인은 아닙니다

`pass`는 현재 자동 검증 조건을 충족했다는 뜻입니다. 결과의 품질과 업무 적합성은 사용자가 근거와 산출물을 확인한 뒤 판단합니다.

### 원본과 화면 정보는 분리됩니다

Run manifest, Evidence와 Artifact는 Engine의 원본 기록입니다. 사용자가 바꾼 표시 이름, 메모, 정렬과 검토 상태는 별도 저장되므로 원본 판정을 덮어쓰지 않습니다.

## 3. 핵심 용어를 쉽게 읽기

| 화면 용어 | 쉬운 뜻 | 예시 |
|---|---|---|
| ProjectRoot | AI 작업을 보관하는 프로젝트 폴더 | `C:\Projects\marketing-plan` |
| Project | 대시보드에 등록된 작업 공간 | 마케팅 콘텐츠 운영 프로젝트 |
| WorkSession | 사용자가 구분하는 하나의 작업 주제 | 7월 콘텐츠 캘린더 만들기 |
| OperationId | 대시보드 요청과 실제 실행을 연결하는 번호 | 새 작업을 만들 때 자동 생성 |
| Run | Engine이 실제로 실행한 한 번의 기록 | 첫 분석, 수정본, 재검증 |
| Evidence | 결과가 맞다고 판단한 근거 | 테스트 결과, 원본 파일, 검증 JSON |
| Artifact | AI가 만들어 낸 결과 파일 | 보고서, 이미지, 코드, Excel |
| Fulfillment | 최초 요청의 완료 조건을 충족했는지 확인 | 필수 산출물 존재와 검증 통과 |
| User Review | 사용자가 실제로 결과를 확인했는지 기록 | 검토 완료와 메모 |

## 4. 가장 안전한 시작 순서

### Step 1. Mock 화면으로 연습

Mock 모드는 실제 운영 Database나 개인 프로젝트를 읽지 않습니다.

```powershell
git clone https://github.com/LEESEOBAEK/Schema-Workflow-Operations-Dashboard.git
Set-Location '.\Schema-Workflow-Operations-Dashboard\apps\dashboard-vnext'
corepack pnpm install --frozen-lockfile
$env:NUXT_DASHBOARD_DATA_MODE = 'mock'
corepack pnpm dev --port 3215
```

브라우저에서 `http://localhost:3215/hybrid`를 엽니다.

### Step 2. 화면에서 한 Run 읽기

1. 프로젝트 하나를 선택합니다.
2. 왼쪽 작업 세션에서 항목 하나를 선택합니다.
3. 가운데 Run 목록에서 실행 기록을 선택합니다.
4. 상태와 다음 행동을 읽습니다.
5. 근거와 산출물 목록을 엽니다.
6. 파이프라인 상세 검토에서 요청부터 완료 조건까지 확인합니다.
7. 충분히 확인했다면 사용자 검토를 완료합니다.

이 단계에서는 새 작업을 만들거나 자동 실행을 켤 필요가 없습니다.

### Step 3. 테스트 프로젝트 연결

실제 업무 폴더보다 먼저 빈 테스트 폴더를 준비합니다.

```powershell
$practiceRoot = Join-Path $HOME 'Desktop\SchemaWorkflowPractice'
New-Item -ItemType Directory -Force -Path $practiceRoot
```

대시보드에서 이 폴더를 ProjectRoot로 등록한 뒤 프로젝트 상태와 스킬 상태가 정상인지 확인합니다.

### Step 4. 첫 작업 세션 생성

작업 템플릿에서 `새 프로젝트 시작`을 선택하고 다음 내용을 입력합니다.

| 입력 | 예시 |
|---|---|
| 작업 제목 | 마케팅 콘텐츠 운영 흐름 정리 |
| 현재 상황 | 여러 채널의 게시 일정과 담당자가 흩어져 있어 한눈에 보기 어렵다. |
| 기준 Run | 첫 작업이면 비워 둠 |
| 제약조건 | 실제 게시와 외부 전송은 하지 않고 기획안까지만 작성한다. |

템플릿은 답을 자동으로 확정하는 기능이 아닙니다. 사용자의 상황과 경계를 AI가 놓치지 않게 전달하는 실행 기준입니다.

### Step 5. AI CLI에서 실행

1. Codex, Claude Code 또는 Antigravity를 선택합니다.
2. 대시보드가 표시한 ProjectRoot와 준비 명령을 확인합니다.
3. 해당 프로젝트를 VS Code 또는 터미널에서 엽니다.
4. 플랫폼에서 Schema Workflow 스킬이 인식되는지 확인합니다.
5. 대시보드가 준비한 요청을 실행합니다.

플랫폼마다 명령 형식은 다르지만 `ProjectRoot`, `OperationId`, 작업 세션 참조와 원문 파일은 동일한 계약으로 전달됩니다.

### Step 6. Run 연결과 결과 확인

CLI 작업이 끝난 뒤 대시보드에서 새로고침하거나 Run 연결 확인을 실행합니다.

- Run이 연결되면 작업 세션 아래에 실행 기록이 나타납니다.
- 연결되지 않으면 새 작업을 반복 생성하기 전에 OperationId와 Run manifest를 확인합니다.
- 산출물만 있고 Run이 없다면 Workflow Engine을 사용하지 않은 일반 AI 작업일 수 있습니다.

## 5. 상태별로 무엇을 해야 하나

| 상태 | 의미 | 사용자의 다음 행동 |
|---|---|---|
| 통과 | 현재 자동 검증 조건을 충족 | 근거와 산출물을 읽고 사용자 검토 진행 |
| 근거 부족 | 결과는 있지만 필수 근거나 입력이 부족 | 부족한 입력·파일·검증 항목 보강 |
| 보류 | 사용자 결정 또는 외부 조건이 필요 | 질문에 답하거나 조건이 준비될 때까지 유지 |
| 실패 | 계약·파일·검증 중 명확한 오류 발생 | 오류 코드와 실패 단계를 확인해 수정 후 재실행 |
| 미검토 | 자동 검증과 별개로 사용자가 아직 확인하지 않음 | 결과를 읽고 검토 완료 또는 수정 요청 |

## 6. 새 작업·이어가기·분기 선택

### 새 작업

기존 결과에 의존하지 않는 독립된 문제입니다. 기준 Run을 선택하지 않습니다.

### 이어가기

기존 작업의 목표와 맥락을 유지하며 다음 단계를 수행합니다. 수정, 보강, 후속 산출물 생성에 적합합니다.

### 분기

기존 Run을 참고하지만 다른 방향을 독립적으로 실험합니다. A/B 비교, 다른 디자인과 대안 검증에 적합합니다.

관계가 모호하면 자동으로 추정하지 말고 보류 상태에서 기준 Run을 사용자가 선택하는 것이 안전합니다.

## 7. 처음에는 이렇게 운영하세요

1. 실제 자료가 없는 테스트 폴더에서 시작합니다.
2. 한 작업 세션에 한 가지 핵심 문제만 넣습니다.
3. 자동 승인보다 VS Code 열기와 수동 실행을 먼저 사용합니다.
4. 통과 숫자만 보지 말고 근거와 산출물을 한 번씩 엽니다.
5. 결과가 마음에 들지 않으면 원본 Run을 삭제하지 말고 이어가기 또는 분기를 사용합니다.
6. 사용자 검토 메모에 수정 이유와 다음 행동을 짧게 남깁니다.
7. 반복 사용으로 가치가 확인된 템플릿만 확장합니다.

## 8. 자주 생기는 문제

### `pnpm` 명령을 찾지 못함

전역 `pnpm` 대신 `corepack pnpm`을 사용합니다. Windows 통합 Bundle을 설치했다면 제공된 Dashboard 실행기를 사용하는 편이 간단합니다.

### 프로젝트는 보이지만 Run이 없음

- ProjectRoot가 실제 작업 폴더와 같은지 확인합니다.
- `outputs/workflows` 아래에 Run 폴더가 생성됐는지 확인합니다.
- 일반 AI 작업만 수행하고 Workflow Engine을 실행하지 않았는지 확인합니다.

### CLI에서 스킬을 인식하지 못함

대시보드의 스킬 상태에서 플랫폼별 설치 여부와 버전을 확인합니다. 수정된 unmanaged 스킬은 자동으로 덮어쓰지 않으므로 사용자가 변경 내용을 먼저 검토해야 합니다.

### CLI 작업은 끝났지만 세션에 연결되지 않음

OperationId가 Run manifest에 보존됐는지 확인합니다. 이어가기·분기라면 기준 Run과 관계 계약도 함께 확인합니다.

### 통과했는데 검토 대기에 표시됨

정상 동작입니다. 자동 검증을 통과했지만 사용자가 아직 결과를 읽지 않았다는 의미입니다.

### 근거 부족이 계속 표시됨

버그라고 단정하기 전에 입력 파일, 필수 필드, Evidence와 validation_needed를 확인합니다. 근거가 없으면 상태를 억지로 통과로 바꾸지 않는 것이 이 도구의 기본 원칙입니다.

## 9. 안전 경계

- 실제 운영 Database와 Run manifest를 수동으로 편집하지 않습니다.
- 작업 세션 제거와 원본 Run 삭제를 같은 행동으로 취급하지 않습니다.
- 자동 실행은 신뢰하도록 등록한 테스트·프로젝트 경로에서만 사용합니다.
- Claude Code, Codex와 Antigravity의 전체 권한 모드는 각 플랫폼의 보안 책임을 따릅니다.
- 비밀값, 개인정보와 실제 고객 데이터는 공개 Mock 프로젝트에 넣지 않습니다.
- AI의 숨은 추론 과정은 수집 대상이 아닙니다. 관찰 가능한 입력, 근거, 산출물과 상태만 기록합니다.

## 10. 첫 사용 완료 체크리스트

- [ ] Mock 대시보드를 열었다.
- [ ] Project, WorkSession과 Run의 차이를 확인했다.
- [ ] Run 하나의 근거와 산출물을 열어 봤다.
- [ ] 통과와 사용자 검토 완료가 다르다는 것을 이해했다.
- [ ] 빈 테스트 ProjectRoot를 등록했다.
- [ ] 작업 템플릿으로 첫 WorkSession을 만들었다.
- [ ] AI CLI에서 스킬과 프로젝트 경로를 확인했다.
- [ ] 첫 Run을 작업 세션에 연결했다.
- [ ] 결과를 검토하고 다음 행동을 기록했다.

여기까지 완료하면 기본 운영 흐름을 익힌 것입니다. 그 이후에 이어가기, 분기, 자동 실행과 직무별 템플릿을 단계적으로 확장하는 것이 좋습니다.
