# 1. 비전 (Why)

### 프로젝트 목적

> Codex, Claude Code, Antigravity 등 여러 AI 도구에서 진행한 작업과 결과물을 한곳에서 확인하고, 이전 작업을 안전하게 이어갈 수 있는 개인용 작업 관리 시스템을 만든다.

AI 작업은 플랫폼, 터미널과 폴더별로 분산되기 쉽다. 이 프로젝트는 사용자의 요청, 실행 기록, 판단 근거, 결과물과 다음 행동을 일정한 구조로 연결하여 작업 맥락의 손실을 줄이는 것을 목적으로 한다.

### 기대 효과

- 여러 AI 도구에서 진행한 작업을 프로젝트별로 확인할 수 있다.
- 어떤 요청에서 어떤 결과물이 나왔는지 추적할 수 있다.
- 이전 작업 이어가기와 새로운 방향의 작업을 구분할 수 있다.
- 결과물 존재 여부와 검증 상태를 함께 확인할 수 있다.
- 정보가 부족한 결과를 억지로 완료 처리하지 않을 수 있다.

# 2. 해결하려는 문제

### 현재 문제

AI 에이전트 작업은 여러 터미널과 플랫폼에 분산된다. 결과 파일이 만들어져도 어떤 요청과 실행에서 나온 것인지 찾기 어렵고, 같은 프로젝트를 동시에 실행하면 저장 위치가 달라지거나 작업 기록이 중복될 수 있다.

또한 AI가 작업 완료를 보고하더라도 실제 결과물과 검증 상태가 일치하는지 별도로 확인해야 한다.

### 기존 방법의 한계

- 채팅 기록과 폴더만으로는 장기간의 작업 흐름을 추적하기 어렵다.
- 실행 번호가 길어 사람이 작업을 구분하기 어렵다.
- AI 도구마다 스킬 설치와 실행 방식이 다르다.
- 긴 요청이 전달 과정에서 잘리면 결과와 완료 기준이 달라질 수 있다.
- 대시보드의 표시 상태와 실제 저장 상태가 달라질 수 있다.
- 병렬 작업에서 경로 분산과 중복 실행이 발생할 수 있다.

### 해결 방향

Python 엔진은 입력 정리, 저장 형식 검사, 실행 기록과 결과 검증을 담당한다. 외부 AI 도구는 해석과 결과물 생성을 담당하며, Nuxt 대시보드는 실제 저장 데이터를 읽어 프로젝트, 작업 세션, 결과물과 상태를 표시한다.

원본 결과물은 수정하지 않고, 작업 이름과 연결 관계 같은 관리 정보만 별도로 저장한다.

# 3. 목표 사용자 및 사용 맥락

### 대상 사용자

- 여러 AI CLI를 함께 사용하는 개인 개발자
- AI 자동화와 에이전트 작업 방식을 학습하는 사용자
- 장기 프로젝트의 실행 기록과 결과물을 관리하려는 사용자

### 사용 환경

- 장소: 개인 로컬 개발 환경
- 디바이스: Windows 11 데스크톱
- 주요 도구: VS Code, PowerShell, Python, Nuxt
- AI 환경: Codex CLI, Claude Code, Antigravity
- 사용 상황: 작업 준비, 실행, 결과 연결, 검토와 후속 작업 결정

### 대표 사용 시나리오

1. 사용자가 대시보드에서 프로젝트를 선택한다.
2. 새 작업, 이어가기 또는 별도 방향 작업을 선택한다.
3. 문제 상황과 원하는 결과를 입력한다.
4. 시스템이 프로젝트 경로, 스킬 상태와 실행 내용을 준비한다.
5. 사용자가 VS Code 터미널에서 AI 도구를 실행한다.
6. 생성된 실행 기록과 결과물이 작업 세션에 연결된다.
7. 사용자는 통과, 근거 부족, 보류 상태와 다음 행동을 확인한다.

# 5. 제약조건

### 기술적 제약

- Windows의 경로 길이와 파일 잠금 문제를 고려해야 한다.
- 외부 AI CLI의 실행 방식이 업데이트로 달라질 수 있다.
- 대시보드와 Python 엔진은 파일을 통해 상태를 공유한다.
- 현재 데이터는 JSON, JSONL, Markdown과 일반 산출물로 구성된다.
- 대용량 프로젝트는 전체 파일을 반복해서 읽으면 속도가 느려질 수 있다.

### 사용자 경험 제약

- 긴 실행 번호는 보존하되 이해하기 쉬운 작업 이름과 함께 표시해야 한다.
- 작은 화면에서도 프로젝트와 작업 세션 이름이 보여야 한다.
- 통과, 근거 부족, 보류와 충돌 상태를 빠르게 구분할 수 있어야 한다.
- 복잡한 기술 용어보다 사용자가 해야 할 다음 행동을 먼저 보여줘야 한다.

### 운영 제약

- 현재는 개인 로컬 환경을 기준으로 한다.
- 원본 파일의 자동 삭제, 이동과 덮어쓰기를 허용하지 않는다.
- 되돌리기 어려운 실행은 사용자 승인을 요구한다.
- 실제 사용자 데이터와 절대 경로는 공개 저장소에서 제외한다.

### 기타

- AI가 추론한 내용은 확인된 사실과 구분해야 한다.
- 실측하지 않은 성능과 지원 범위를 완료된 기능처럼 표현하지 않는다.

# 6. 성공 기준

### 기능 성공 기준

- 독립 작업, 이어가기와 별도 방향 작업이 올바른 세션에 연결된다.
- 존재하지 않는 실행 기록과 잘못된 관계를 거절한다.
- 원문 요청, 결과물과 검증 상태가 실제 파일과 일치한다.
- 원본 결과물을 변경하지 않고 이름과 관계를 관리할 수 있다.

### 사용자 성공 기준

- 사용자가 현재 프로젝트, 작업 세션과 다음 행동을 빠르게 찾을 수 있다.
- 긴 실행 번호를 외우지 않고 사용자 지정 이름으로 작업을 구분할 수 있다.
- 다른 AI 도구를 사용해도 같은 프로젝트 흐름을 유지할 수 있다.

### 성능 성공 기준

- 일반적인 소규모 프로젝트는 지연 없이 탐색할 수 있어야 한다.
- 실제 운영 데이터에서도 화면이 멈추지 않아야 한다.
- 대용량 파일은 필요한 정보만 선택적으로 읽어야 한다.

현재 9개 운영 프로젝트와 68개의 실행 기록을 사용해 기능을 확인했다. 이 수치는 최종 성능 보장이 아니라 실제 사용 검증의 기준선이다.

### 운영 성공 기준

- 설치된 버전과 파일 무결성을 확인할 수 있다.
- 실패 원인과 주요 변경 내역을 기록할 수 있다.
- 기능을 수정한 뒤 기존 동작이 유지되는지 반복 검사할 수 있다.
- 후보 버전을 실제 사용한 뒤 안정 버전 승격 여부를 판단할 수 있다.

# 7. 해결책

### 핵심 아이디어

> AI는 요청 해석과 결과물 생성에 집중하고, Python은 입력·저장·검증을 담당하며, 대시보드는 실제 작업 관계와 상태를 보여준다.

### 해결 방법

1. 사용자의 자연어 요청을 일정한 데이터 형태로 정리한다.
2. 요청의 목적과 상황을 분류한다.
3. 외부 AI 도구가 문서, 코드 또는 아이디어를 생성한다.
4. Python 엔진이 실행 기록과 결과물 존재 여부를 확인한다.
5. 작업 간 이어가기와 분기 관계를 별도로 기록한다.
6. 대시보드가 실제 데이터를 읽어 현재 상태와 다음 행동을 표시한다.
7. 사용자가 결과를 승인, 보류하거나 다시 작업한다.

### 기대 효과

- 작업 맥락과 결과물의 연결 유지
- 경로 이탈, 중복 기록과 잘못된 완료 판정 감소
- AI 도구가 바뀌어도 유지되는 공통 작업 방식 확보
- 실제 실패 기록을 이용한 지속적인 개선 가능

## 애플리케이션 아키텍처 (단일 선택)

☐ 클린(Clean)

☐ 헥사고날(Hexagonal)

☐ Onion

### 선택 이유

화면, 작업 흐름, 데이터 규칙과 파일 저장 역할을 구분하기 쉽고, 각 부분의 오류가 다른 영역으로 퍼지는 것을 줄일 수 있다.

## UI 아키텍처

Nuxt와 Vue를 사용한 로컬 대시보드다. 프로젝트 목록, 작업 세션, 실행 기록과 결과물 상세 영역을 분리하며, 작은 화면과 전체 화면에서 모두 사용할 수 있도록 반응형으로 구성한다.

## 데이터 아키텍처

원본 실행 기록과 결과물은 읽기 중심으로 보존한다. 사용자 표시 이름, 메모와 정렬 정보는 대시보드 전용 데이터로 저장하고, 작업 간 관계는 프로젝트별 관리 폴더에 별도로 저장한다.

안전한 저장과 동시 수정 방지를 적용하며, 화면에 필요한 파생 데이터는 원본에서 다시 만들 수 있게 한다.

## AI 아키텍처

Codex, Claude Code와 Antigravity는 외부 실행 도구다. 공통 스킬이 작업 규칙을 전달하고, Python 엔진이 입력 구조화와 검증을 담당한다. 대시보드는 AI 추론을 직접 수행하지 않는다.

## 통신 방식

- 브라우저와 Nuxt 로컬 서버: HTTP
- Python 엔진과 대시보드: JSON, JSONL, Markdown 파일
- 외부 AI 도구: VS Code 터미널과 PowerShell
- 무결성 확인: SHA-256 파일 지문

## 배포 방식

Windows 사용자 폴더에 후보 버전을 설치하고, 활성 버전 정보와 파일 지문을 이용해 무결성을 검사한다. 실제 작업 검증을 통과한 뒤 안정 버전 승격을 결정한다.

현재 대시보드는 로컬 Nuxt 서버로 실행한다.

# 부록

## A. 주요 문제 해결 사례

### 1. 설치 설정과 실행 설정의 충돌

- 문제: 두 기능이 같은 설정 파일을 서로 다른 형식으로 사용했다.
- 영향: 설치 검사는 통과하지만 실제 작업 실행은 실패했다.
- 해결: 설정의 책임을 분리하고 변경 전 백업과 무결성 검사를 추가했다.
- 배운 점: 하나의 데이터에는 명확한 관리 책임이 필요하다.

### 2. 병렬 작업의 경로 분산과 중복

- 문제: 여러 터미널에서 같은 프로젝트를 실행하면 기록이 다른 위치에 저장됐다.
- 영향: 작업 누락처럼 보이거나 동일 작업이 중복 표시됐다.
- 해결: 프로젝트와 실행별 고유 번호, 저장 위치 규칙과 동시 수정 방지를 적용했다.
- 배운 점: 병렬 실행에서는 작업 소유권과 저장 경계가 필요하다.

### 3. 대시보드와 실제 상태의 불일치

- 문제: 실제 작업은 끝났지만 대시보드에 이전 상태가 남았다.
- 영향: 완료된 작업을 보류 상태로 잘못 판단할 수 있었다.
- 해결: 화면의 임시 상태와 실제 기록을 구분하고 원본 상태를 다시 읽도록 개선했다.
- 배운 점: 화면은 기준 원본이 아니라 실제 데이터를 표현하는 수단이어야 한다.

### 4. 긴 요청의 누락

- 문제: 긴 요청 일부가 전달 과정에서 잘렸다.
- 영향: 원래 요구사항과 다른 결과물이 만들어질 수 있었다.
- 해결: 원문 요청을 파일로 보존하고 파일 지문으로 변경 여부를 확인했다.
- 배운 점: 중요한 요청은 채팅 내용에만 의존하면 안 된다.
